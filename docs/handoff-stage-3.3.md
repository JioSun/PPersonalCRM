## Что уже реализовано

- DRAFT → ISSUED, отзыв ISSUED → DRAFT, отмена DRAFT/ISSUED; PATCH/DELETE только черновика; HTTP issue/revoke/cancel.
- issue_version увеличивается при выставлении; отзыв сохраняет версию, повторное выставление увеличивает снова.
- pay_invoice и pay_invoice_in_db уже существуют в backend/app/services/invoice.py. Они проверяют ожидаемую версию, статус, срок UTC; повтор PAID той же версии не меняет paid_at. Оплата под блокировками общей сделки и счёта, одной транзакцией.
- Занято = ISSUED + PAID; оплачено = PAID; DRAFT/CANCELLED исключены, просроченный ISSUED включён. Суммы Decimal, USD.
- Лимит при выставлении и запрет уменьшить стоимость сделки ниже занятой суммы. Порядок блокировок deal → invoice.
- GET /deals/{id}: DealDetailRead с available_to_issue и remaining_to_pay. GET /deals: DealListRead с paid_amount и remaining_to_pay, агрегирующий LEFT JOIN, пагинация, стабильная сортировка.

## Критичные технические договорённости

- Сервис владеет async with session.begin(). Не передавать ему сессию, в которой авторизация/поиск уже запустили autobegin, без осознанного согласования границ транзакции.
- В существующих mutation routes current_user стоит перед Depends(get_db, use_cache=False). use_cache=False отключает мемоизацию результата зависимости внутри запроса, не очищает Redis, токен или пул соединений. AsyncSession не равна соединению.
- get_invoice_for_transition: найти счёт, заблокировать сделку, перечитать/заблокировать счёт с populate_existing. Связь со сделкой неизменяема. Независимым задачам нужны независимые сессии.
- expected_issue_version приходит из исходного подтверждения/ссылки. Нельзя заменить её актуальной версией из БД при обработке старого задания.
- now — UTC после блокировок; due_date < now.date() означает просрочку, сам день срока допустим. Проверка версии предшествует идемпотентному возврату PAID.
- Для updated_at и сериализации после изменений используется flush → refresh; refresh не сохраняет изменения.
- joinedload/selectinload загружают отношения, не агрегируют суммы и не применяются к скалярной колонке amount. SQL-агрегаты могут возвращать Row; преобразование в Pydantic должно соответствовать схеме и именам/алиасам.
- Не переносить Redis в чистую операцию БД. commit PostgreSQL не откатывается от ошибки кэша/SMTP/брокера.
- Итог оплаты определяется состоянием БД, а не только SUCCESS Celery. Неизвестный task id и PENDING сами по себе не доказывают, что задача действительно принята или выполняется.
