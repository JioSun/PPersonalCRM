# Контрольная точка: безопасные и независимые тесты

Актуализировано 21 сентября 2026 по текущему коду. Этот документ заменяет прежний пакет заданий из переписки. Код реализует пользователь; ментор проверяет пакет целиком. Прогон с миграциями и очисткой ещё не выполнен.

Цель: два последовательных запуска тестов без ручной очистки, случайных 429 и влияния на рабочие данные. До завершения этой точки не добавляем новые бизнес-функции. Параллельный запуск тестов пока не поддерживаем.

Материалы ниже объясняют механизмы. Выбор конкретной организации тестов — рекомендация ментора для проекта, а не дословное требование документации или книги. Из Full Stack Testing применяем принципы устойчивой автоматизированной обратной связи и проверки хранения данных (главы 3 и 5). Читать книгу целиком для выполнения пакета не требуется.

## Уже сделано — сохранить

- Значение REDIS_DB в os.environ теперь строковое.
- Middleware получает provider из app.state, тест передаёт асинхронный генератор.
- Генератор middleware обёрнут в aclosing; лимит проверяется до call_next.
- Исходный provider сохраняется до try и восстанавливается в finally.
- Redis очищается до и после теста.
- Тестовый SQLAlchemy engine освобождается через dispose в finally.

Это оценка кода, не подтверждение успешного запуска. Механизмы описаны в [os.environ](https://docs.python.org/3.12/library/os.html#os.environ), [aclosing](https://docs.python.org/3.12/library/contextlib.html#contextlib.aclosing) и [AsyncEngine.dispose](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html#sqlalchemy.ext.asyncio.AsyncEngine.dispose).

## 1. Исправить аргументы и типы проверок адресов

**Где:** backend/tests/conftest.py, validate_test_database, validate_test_redis и их вызовы.

**Проблема:** validate_test_database требует host и name, а получает один аргумент settings.POSTGRES_DB. Это TypeError. В проверке PostgreSQL по ошибке указан порт '6379'; стандартный порт PostgreSQL в твоих Settings — 5432. REDIS_PORT имеет тип int, но сравнивается со строкой '6379', поэтому корректное значение 6379 отклоняется.

**Сделать:** согласовать сигнатуры и вызовы; передавать параметры по именам; сравнивать порты как int. Разрешённые порты соответствуют именно твоей тестовой среде: 5432/6379 — текущие предполагаемые значения, не универсальный закон. При пробросе контейнера порт может быть другим.

**Материалы:** [Python: вызовы функций](https://docs.python.org/3.12/reference/expressions.html#calls) — сопоставление аргументов параметрам; [сравнение значений](https://docs.python.org/3.12/reference/expressions.html#value-comparisons) — различие строки и числа.

**Готово:** проверки принимают разрешённую конфигурацию и отклоняют неверные значения без подключения к сервисам.

## 2. Проверять фактическое подключение до операций с данными

**Проблема:** проверка отдельных значений окружения не гарантирует, что engine и Alembic используют их же. localhost и имя с test также не доказывают, что ресурс можно очищать: он должен быть действительно выделен тестам.

**Сделать:** разобрать используемый PostgreSQL URL через make_url и проверить его host, port, database; сформировать Redis URL из проверенных параметров без второй независимой сборки. Если порт пропущен, явно определить его значение по умолчанию либо требовать явный порт. Проверенный PostgreSQL URL должен совпадать с тем, который использует migrations/env.py. Не печатать пароль. Ограничить разрешённые адреса своей тестовой средой; если позже появится CI, добавить отдельную явную конфигурацию CI, а не отключать проверку.

**Материалы:** [SQLAlchemy: make_url и URL](https://docs.sqlalchemy.org/en/20/core/engines.html#sqlalchemy.engine.make_url); [Alembic: подключение для программного запуска миграций](https://alembic.sqlalchemy.org/en/latest/cookbook.html#sharing-a-connection-across-one-or-more-programmatic-migration-commands). Во втором материале изучить, что фактическое подключение определяется env.py; переписывать всё по примеру необязательно.

**Готово:** неверный хост/порт/имя БД останавливает путь к миграциям и очистке. Тесты проверки используют вымышленные URL и не соединяются с ними.

## 3. Убрать вложенный запуск event loop при миграциях

**Где:** async session_pool и backend/migrations/env.py.

**Проблема:** command.upgrade теперь вызван внутри async-фикстуры. Твой env.py вызывает asyncio.run, который нельзя запускать в том же потоке с уже работающим event loop. Эта ошибка проявится после исправления аргументов проверки.

**Сделать:** для текущей архитектуры вернуть миграции в отдельную обычную синхронную session-фикстуру, зависящую от проверки URL. Асинхронная фикстура engine/pool явно зависит от завершённых миграций. Обычной фикстуре подходит pytest.fixture; async-фикстуре — pytest_asyncio.fixture. Не обходить ошибку библиотекой вложенных event loop.

**Материалы:** [Python: asyncio.run](https://docs.python.org/3.12/library/asyncio-runner.html#asyncio.run) — ограничение вложенного запуска; [pytest: Fixtures can request other fixtures](https://docs.pytest.org/en/stable/how-to/fixtures.html#fixtures-can-request-other-fixtures) — как выразить порядок; [Alembic: Using Asyncio](https://alembic.sqlalchemy.org/en/latest/cookbook.html#using-asyncio-with-alembic) — контекст твоего env.py.

**Готово:** проверка → миграции → engine → сессия теста; нет ошибки asyncio.run и нет зависимости от порядка объявления функций.

## 4. Исправить перебор таблиц

**Где:** truncate_table.

**Проблема:** async for используется для reversed(Base.metadata.tables.values()). Это обычная коллекция Python, а не асинхронный итератор. Наличие await внутри тела не требует async for.

**Сделать:** использовать обычный перебор для подготовки списка таблиц. Асинхронным остаётся выполнение SQL. Названия брать только из доверенных метаданных приложения, учитывать схему и корректное quoting идентификаторов.

**Материалы:** [Python: async for](https://docs.python.org/3.12/reference/compound_stmts.html#the-async-for-statement) — требование асинхронного итератора; [SQLAlchemy: MetaData.tables](https://docs.sqlalchemy.org/en/20/core/metadata.html#sqlalchemy.schema.MetaData.tables) — коллекция метаданных.

**Готово:** получение списка таблиц выполняется без БД и без TypeError про __aiter__.

## 5. Учесть внешние ключи при TRUNCATE

**Проблема:** отдельный TRUNCATE каждой таблицы без CASCADE не становится допустимым от обратного порядка. PostgreSQL учитывает существующие FK даже при пустых дочерних таблицах.

**Сделать:** перечислить все связанные таблицы приложения в одной команде TRUNCATE. Не включать alembic_version. Не добавлять CASCADE только ради исчезновения ошибки. RESTART IDENTITY сбрасывает sequences; твои ULID он не сбросит. InvoiceCounter очищается как отдельная таблица.

**Материал:** [PostgreSQL 17: TRUNCATE](https://www.postgresql.org/docs/17/sql-truncate.html) — Parameters и Notes: FK, CASCADE/RESTRICT, транзакционность.

**Готово:** после очистки нет пользователей, клиентов, сделок, счетов и счётчиков; версия миграций сохранена.

## 6. Отделить транзакцию очистки от тестовой сессии

**Проблема:** очистка делается сессией теста. Перед заключительным TRUNCATE вызывается commit, а после него — close без commit. Последняя очистка может откатиться. Commit в teardown также может неожиданно сохранить незавершённые изменения теста.

**Сделать:** отдельная короткая транзакция очистки до теста; отдельная сессия для теста; после её закрытия — новая транзакция очистки. Зафиксировать именно очистку. Финальная уборка должна выполняться и при исключении. Ранее закоммиченные CRUD-записи обычным rollback уже не удалить.

**Материалы:** [SQLAlchemy: AsyncEngine.begin](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html#sqlalchemy.ext.asyncio.AsyncEngine.begin) — транзакционный контекст; [pytest: Safe teardowns](https://docs.pytest.org/en/stable/how-to/fixtures.html#safe-teardowns) — организация уборки после ошибки.

**Готово:** очистка зафиксирована; даже тест с ошибкой SQL не оставляет данные следующему тесту. Пока не добавляем альтернативу с внешней транзакцией/SAVEPOINT.

## 7. Завершить изоляцию и владение Redis-пулом

**Проблема:** flushdb удаляет всю выбранную логическую БД. Пул создан отдельно и передан в Redis(connection_pool=...), поэтому закрытие клиента не следует считать закрытием принадлежащего фикстуре внешнего пула.

**Сделать:** после проверки выделенного адреса очищать тестовую БД перед/после теста; закрывать собственный пул даже при ошибке flushdb. Выбрать один понятный вариант владения: клиент владеет пулом либо фикстура закрывает их явно. База /5 должна быть зарезервирована только для тестов. Логическая БД — разделение ключей, не защита от доступа других клиентов.

**Материалы:** [Redis: FLUSHDB](https://redis.io/docs/latest/commands/flushdb/) — область удаления; [redis-py: asyncio examples](https://redis.readthedocs.io/en/stable/examples/asyncio_examples.html) — раздел Connecting and Disconnecting, варианты владения пулом.

**Готово:** каждый последовательный тест начинает с пустыми счётчиками; рабочие базы не меняются; созданный пул освобождён. Параллельные тесты с общей очищаемой БД запрещены в этом пакете.

## 8. Полностью восстанавливать подмены приложения

**Проблема:** provider уже восстанавливается правильно, но dependency_overrides.clear() стирает и подмены, существовавшие до фикстуры.

**Сделать:** до try сохранить копию исходного словаря; в finally вернуть прежнее содержимое и provider. Не сохранять только ссылку на изменяемый словарь: она будет видеть внесённые изменения.

**Материалы:** [FastAPI: Testing Dependencies with Overrides](https://fastapi.tiangolo.com/advanced/testing-dependencies/) — что хранит словарь; [Python: dict.copy](https://docs.python.org/3.12/library/stdtypes.html#dict.copy) — поверхностная копия; [pytest: Safe teardowns](https://docs.pytest.org/en/stable/how-to/fixtures.html#safe-teardowns).

**Готово:** фикстура восстанавливает исходное состояние, включая заранее установленную постороннюю подмену.

## 9. Исправить диагностику регистрации и login

**Проблема:** в active_user и other_active_user извлечение access_token по-прежнему идёт до assert status_code. Ответ регистрации не проверяется. Поэтому ошибочный login снова даёт KeyError.

**Сделать:** сохранить ответ регистрации → проверить 200 по текущему контракту → выполнить login через data → проверить 200 → проверить непустой access_token → собрать Authorization. Сообщать шаг и статус; не выводить пароли и токены. Удалить print полного успешного ответа login из тестов.

**Материалы:** [pytest: assertions](https://docs.pytest.org/en/stable/how-to/assert.html#asserting-with-the-assert-statement) — диагностические проверки; [FastAPI: OAuth2 password flow](https://fastapi.tiangolo.com/tutorial/security/simple-oauth2/) — форма username/password.

**Готово:** отказ регистрации или login даёт ошибку соответствующего шага, а не KeyError. Для проверки диагностики не нужны реальные истёкшие токены.

## 10. Упростить контракт пользовательских фикстур

**Проблема:** active_user возвращает кортеж, other_active_user — словарь. test_client_works запрашивает active_user, хотя проверяет запрос без токена; это создаёт лишние auth-запросы.

**Сделать:** выбрать один формат результата обеих фикстур с явно понятными полями. Получение refresh_token оставить доступным для отдельного сценария. Удалить ненужную зависимость active_user из теста без авторизации.

**Материал:** [pytest: Requesting fixtures](https://docs.pytest.org/en/stable/how-to/fixtures.html#requesting-fixtures) — параметр теста запускает подготовку зависимости, даже если тело теста её результат не использует.

**Готово:** назначение полей очевидно; запрос без токена не требует регистрации и login.

## 11. Исправить сценарий доступа к чужому счёту

**Проблема:** test_create_invoice_with_other_user не передаёт обязательный due_date и чужой deal_id в итоговом запросе, ожидает 401 с валидным токеном. Так проверяется другой путь ошибки.

**Сделать:** подготовить A/B; отправить полный валидный payload от A со своим client_id и чужим deal_id; ожидать 404 по текущему контракту проекта; подтвердить отсутствие созданного счёта. Отдельный сценарий — чужой client_id. Для проверки связей своих клиентов достаточно записать задачу следующего этапа: здесь не расширяем доменную реализацию.

**Материалы:** [FastAPI: Testing](https://fastapi.tiangolo.com/tutorial/testing/) — запросы, JSON и assertions; [FastAPI: Handling Errors](https://fastapi.tiangolo.com/tutorial/handling-errors/) — HTTPException. Выбор 404 здесь основан на текущем контракте проекта, а не является универсальным требованием FastAPI.

**Готово:** тест дошёл до проверки владельца; форма запроса корректна; чужая связь отвергнута без записи.

## 12. Доказать поведение лимитера

**Проблема:** 429 уже наблюдался, но это не доказывает нужную границу лимита, отсутствие вызова роута и cleanup provider.

**Сделать:** тест разрешённого запроса; тест шестого auth-запроса в одном окне; доказательство, что заблокированный запрос не вызывает обработчик; тест закрытия provider при 429 и исключении. Для middleware допустим маленький тестовый app с обработчиком-счётчиком и управляемой подставной Redis-зависимостью. Отдельно интеграционно проверить счётчик настоящего тестового Redis. Не ждать 60 секунд: проверку окна/TTL организовать отдельным управляемым сценарием.

**Материалы:** [Python: AsyncMock](https://docs.python.org/3.12/library/unittest.mock.html#unittest.mock.AsyncMock) — assert_awaited/assert_not_awaited; [Python: aclosing](https://docs.python.org/3.12/library/contextlib.html#contextlib.aclosing) — завершение при раннем выходе; [FastAPI: middleware](https://fastapi.tiangolo.com/tutorial/middleware/) — положение call_next.

**Готово:** блокировка происходит до обработчика, генератор завершён, следующий независимый тест не наследует счётчик. Атомарность INCR/EXPIRE остаётся отдельной задачей надёжности лимитера, не считается решённой этим пакетом.

## 13. Завершить пакет воспроизводимым прогоном

**Сделать:** исправить новые ошибки форматирования и типов в затронутых файлах; прислать пакет на ревью перед прогоном очистки. После проверки адресов и области удаления — два последовательных запуска набора; затем смена порядка отдельных тестов регистрации/доступа. Любое новое падение фиксировать со статусом, названием теста и причиной; не скрывать sleep, увеличением лимита или новым случайным email.

**Материалы:** [pytest: запуск тестов](https://docs.pytest.org/en/stable/how-to/usage.html) — выбор файлов и отдельных тестов; [pytest: flaky tests](https://docs.pytest.org/en/stable/explanation/flaky.html) — неконтролируемое состояние и зависимость от порядка.

**Готово:** два чистых прогона без ручной очистки; регрессия повторного email в одном тесте сохранена; проверки доступа/лимитера проходят; секреты отсутствуют в диагностике.

## Порядок работы и сдача

Выполнять блоками: 1–3 (запуск и адреса) → 4–7 (хранилища) → 8–10 (фикстуры) → 11–13 (сценарии и доказательство).

Не требуется отчитываться после каждой строки. На ревью прислать: «Пакет готов», краткий список решений по тестовым адресам и владению ресурсами, оставшиеся вопросы. Ментор перечитывает весь пакет и возвращает один сводный список. До безопасного прогона статусы задач означают «реализовано», а не «проверено».

Следующий этап после приёмки: бизнес-правила счетов, оплаты, валют и дашборда. Очереди, AI, архитектурные переписывания и новые инструменты сюда не добавляем.
