## Важные технические договорённости

- Сервис открывает async with session.begin(); ему нужна сессия без начатой транзакции.
- Авторизация делает SELECT и запускает autobegin. В текущем HTTP-подходе current_user:
  Depends(get_current_active_user) объявляется ПЕРЕД session: Depends(get_db, use_cache=False).
  Пользователь несколько раз правил не тот фрагмент/не сохранял изменения; сверять диск.
- get_invoice_for_transition сначала читает счёт, затем блокирует сделку, затем перечитывает
  и блокирует счёт с populate_existing=True. Связь со сделкой неизменяема.
- Проверки статуса и запись происходят под блокировками в одной транзакции.
- Порядок блокировок общий: deal → invoice. Не добавлять commit в CRUD посреди операции.
- refresh не сохраняет изменения. Перед refresh изменённого объекта нужен flush.
- updated_at вычисляется через onupdate=func.now(); незагруженное значение при синхронной
  Pydantic-сериализации вызывало MissingGreenlet. В сервисе PATCH есть flush → refresh;
  HTTP переходов делает refresh после успешного сервиса.
- pay_invoice принимает expected_issue_version извне; нельзя подставлять текущую версию из БД.
  Сначала проверить версию, затем ранний выход для PAID той же версии, затем ISSUED и срок.
- now — aware datetime UTC. В сервисе оплаты время берётся после получения блокировок.
  Просрочка: due_date < now.date(); сам день срока допустим.
- Успех оплаты выставляет PAID, is_paid=True, paid_at=now; версия не меняется.
- Для конкурентных задач отдельные сессии. Не использовать одну AsyncSession в gather.
- Event показывает порядок Python-кода, не сам факт SQL-блокировки.
  Контролируемый тест получает PID внутри уже начатой сервисом транзакции, наблюдает через
  третью сессию, ограничивает ожидание таймаутом и завершает задачи до закрытия сессий.

## С чего начать 3.2

Сначала прочитать актуальные domain.md, сервис выставления и модель/CRUD сделки.
Первое небольшое задание — только расчёт сумм счетов сделки: занятой суммы (ISSUED + PAID) и оплаченной суммы (PAID). Подключение проверки лимита к выставлению — вторая задача, отдельно от первой.

Правила:
- доступно для выставления = сумма сделки − сумма счетов ISSUED и PAID;
- новый счёт при выставлении не должен превысить этот лимит;
- DRAFT и CANCELLED в лимите не участвуют;
- просроченный ISSUED участвует; PAID продолжает участвовать;
- при недостаточном лимите статус DRAFT и issue_version остаются прежними;
- суммы Decimal, USD; стоимость сделки не уменьшается от выставления/оплаты;
- проверка и переход атомарны под блокировкой общей сделки, иначе два выставления могут
  одновременно потратить один лимит;
- в границах всего этапа также учитывать запрет уменьшения стоимости сделки ниже суммы
  ISSUED + PAID; не навешивать это сразу на первый маленький шаг.

Не переносить сюда работу со ссылками, Celery, письмами и UI из 3.3.
Перед новым заданием кратко подтвердить понимание контракта, без повторного длинного аудита.
