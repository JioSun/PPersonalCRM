# Этап 4 — воспроизводимый релиз PersonalCRM

Контракт от 21 октября 2026. Этап 3 закрыт в согласованных границах; последняя регрессия — 413 passed in 114.90s. Этот документ заменяет старые указания раздела «Этап 4» в personalcrm-roadmap.md. Всего **8 задач, завершено 0, осталось 8**. Исправления ревью не создают новых задач.

## Результат и границы

Другой разработчик может запустить приложение по документации; CI проверяет изменения; демонстрационная установка доступна по HTTPS; данные переживают пересоздание контейнера и восстанавливаются из резервной копии. Это один сервер и небольшой демонстрационный сервис, не промышленная платформа с высокой доступностью.

PDF исключён. Celery, напоминания, реальный эквайринг, новый frontend, Kubernetes, микросервисы, Prometheus/Grafana, нагрузочное тестирование без конкретной проблемы не входят. Закрытые доменные задачи не открываем заново. Реальные AI/SMTP-запросы и платные ресурсы — только по отдельному разрешению. Оплата сервера/домена и публикация требуют конкретного согласования перед действием; локальную подготовку выполняем заранее.

Бизнес-логику и содержательные изменения пишет пользователь. Ассистент готовит однотипные тесты, помогает с рутинной конфигурацией по просьбе; первый новый приём тестирования объясняется до самостоятельной попытки. По одной законченной задаче: проблема, поведение, критерии, границы. Выбор реализации за пользователем. Ревью всего изменённого участка, без повторных опросов; косметика не блокирует результат. Делегирование не считается недостатком самостоятельности. Изменение объёма явно согласуется с пересчётом задач и времени.

## 4.1. Локальный запуск и сохранность PostgreSQL — 3–5 часов

Проблема: Compose не подтверждён как воспроизводимый запуск; postgres:17 монтирует родительский путь /var/lib/postgresql, а не явно проверенный PGDATA. Нельзя считать сохранность доказанной по одному restart.

Ожидается: по описанным настройкам запускаются PostgreSQL, Redis и API; схема создаётся миграциями. БД и Redis не публикуются на всех сетевых интерфейсах. При необходимости локального доступа порты привязаны к loopback. Конфигурация приложения и контейнеров согласована.

Приёмка: на отдельных временных ресурсах создать клиентскую запись, пересоздать контейнер PostgreSQL без удаления volume, проверить запись независимым запросом. Проверить миграции на пустой БД. Рабочий volume не удалять и не переносить без отдельного безопасного плана. Существующий compose.test.yaml остаётся изолированным. Дополнить .env.example актуальными переменными без значений реальных секретов.

Материалы: [Docker Compose startup order](https://docs.docker.com/compose/how-tos/startup-order/) — раздел Control startup и пример service_healthy; [официальный образ PostgreSQL](https://hub.docker.com/_/postgres) — только PGDATA и Where to Store Data, внимательно различать версии 17 и 18+. Пока без reverse proxy и CI.

## 4.2. Воспроизводимый образ приложения — 3–5 часов

Ожидается: зависимости из uv.lock, без обновления lock при сборке/старте; runtime от непривилегированного пользователя; секреты и локальное окружение не попадают в образ. Неиспользуемые системные PDF-библиотеки удалены после проверки необходимости. Шаблоны и HTML доступны в контейнере.

Приёмка: образ собирается из чистого контекста, запускает API, открывает платёжную страницу, выполняется с UID != 0. Проверены исключения .dockerignore. Версия uv закреплена; стратегия тегов базового образа записана. Многостадийность допустима, но не обязательна ради формы.

Материалы: [uv in Docker](https://docs.astral.sh/uv/guides/integration/docker/) — Installing uv и Installing a project; [Dockerfile USER](https://docs.docker.com/reference/dockerfile/#user) — описание и пример USER. Не читать весь справочник Dockerfile.

## 4.3. Проверки Ruff и mypy — 4–7 часов

Ожидается: закреплены команды и область проверки. Ruff проверяет backend; mypy — backend/app, без требования строгой типизации всех тестов и исторических миграций. Не повышаем strict до true в рамках этапа.

Приёмка: согласованные команды проходят; исправления типов соответствуют реальным возвращаемым значениям; нет массового подавления ошибок через Any/ignore. Существующее ignore_missing_imports не маскирует ошибки собственного кода. После содержательных изменений проходят затронутые тесты. Автоформатирование/импорты может выполнить ассистент, существенные ошибки разбираем с пользователем.

Материалы: [Ruff linter](https://docs.astral.sh/ruff/linter/) — ruff check и исправления, без всей таблицы правил; [mypy existing code](https://mypy.readthedocs.io/en/stable/existing_code.html) — Start small и Run mypy and fix errors. Число ошибок сейчас не измерено: это основная неопределённость оценки, не повод для общего аудита.

## 4.4. CI — 3–5 часов

Ожидается: на push/PR запускаются согласованные проверки, тесты на отдельных PostgreSQL/Redis и сборка образа. Основной вариант — GitHub Actions, если репозиторий размещён на GitHub; другой хост обсуждаем перед этой задачей.

Приёмка: зафиксирован успешный удалённый запуск; провал проверки делает workflow красным. Тесты не требуют production-секретов и не отправляют письма/AI-запросы. Версии зависимостей берутся из lock. Адреса сервисов соответствуют защитным проверкам conftest (localhost:55432 и localhost:56379/5), защиту не отключаем ради CI. Автодеплой не требуется.

Материалы: [GitHub Actions Python](https://docs.github.com/en/actions/use-cases-and-examples/building-and-testing/building-and-testing-python) — создание workflow и тестирование; [uv GitHub Actions](https://docs.astral.sh/uv/guides/integration/github/) — установка uv/Python и синхронизация зависимостей. Первый workflow объясняем как новый инструмент, не требуем его знания заранее.

## 4.5. Готовность и диагностика — 4–7 часов

Ожидается: liveness отражает работу процесса, readiness — возможность работы с PostgreSQL и Redis с ограниченным временем проверки; внешний AI/SMTP не вызываются health-проверкой. Ресурсы, которыми владеет приложение, закрываются при завершении. В логах можно сопоставить запрос и ошибку по request_id.

Приёмка: readiness 200 при доступных зависимостях и 503 при их отказе; liveness не требует Redis и не блокируется общим лимитером. Проверено завершение ресурсов. Логи не раскрывают пароль, JWT, платёжный токен в URL, SMTP-пароль, API-ключ или текст заметки; это относится и к access-логам. HTTP-ошибка и запись лога имеют общий идентификатор. Не создаём новый observability-стек и не меняем поведение всех бизнес-роутов при отказе Redis.

Материалы: [FastAPI lifespan](https://fastapi.tiangolo.com/advanced/events/) — Lifespan и asynccontextmanager до Alternative Events; [Python Logging HOWTO](https://docs.python.org/3/howto/logging.html) — Logging from multiple modules и Changing the format of displayed messages. Ассистент подготовит тесты отказов до ревью.

## 4.6. Резервная копия и восстановление — 3–5 часов

Ожидается: документированная команда резервного копирования и восстановления в отдельную пустую БД, без перезаписи рабочей. Redis не является источником финансовых данных и не требует восстановления кэша.

Приёмка: восстановлены несколько связанных записей клиент → сделка → счёт, проверены значения, связи и статус; одного exit code pg_dump недостаточно. Указаны место хранения, ручная периодичность для демо и риск потери данных после последней копии. Не заявлять автоматические backup, если их нет. Backup не коммитится и содержит чувствительные данные. Ассистент готовит повторяемую проверку; первое восстановление пользователь проходит после объяснения.

Материалы: [PostgreSQL SQL dump](https://www.postgresql.org/docs/17/backup-dump.html) — 25.1 и Restoring the Dump; [pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html) — Description и Examples для выбранного формата. Физическая репликация и PITR вне этапа.

## 4.7. Демонстрационный релиз по HTTPS — 4–7 часов

Ожидается: выбран один сервер/хостинг и способ TLS; наружу открыты только необходимые публичные порты, PostgreSQL/Redis закрыты. Публичная ссылка оплаты использует правильный HTTPS base URL. Секреты задаются на сервере, не в Git/образе. Миграции выполняются явным шагом выпуска.

Приёмка: TLS валиден, основной сценарий с синтетическими данными проходит через внешний адрес; есть запись версии и инструкция возврата предыдущего образа с оговоркой о совместимости схемы. Настоящие письмо/AI — только по разрешению; контролируемые тесты не выдаём за реальную доставку. Не обещаем zero downtime и автоматический откат миграций. Если домен/сервер недоступен, задача остаётся открытой, а локальный запуск не выдаётся за публикацию.

Материалы: [FastAPI deployment concepts](https://fastapi.tiangolo.com/deployment/concepts/) — HTTPS, Running on Startup, Restarts, Previous Steps Before Starting; [Caddy automatic HTTPS](https://caddyserver.com/docs/automatic-https) — Overview и требования DNS/портов. Caddy — предлагаемый простой вариант, не обязательная технология. Инструкции выбранного хостинга добавляются вместо второго материала, если он управляет TLS сам.

## 4.8. Инструкция и итоговая приёмка — 3–5 часов

Ожидается: README описывает назначение, границы демооплаты, компоненты, env, запуск, миграции, тесты, backup/restore и ограничения. Короткий release checklist с проверяемыми результатами.

Приёмка: запуск по README на чистом отдельном окружении, основной сценарий и регрессия проходят, ссылки доступны. Записаны известные ограничения: качество AI не гарантируется схемой, SMTP acceptance не равно доставке, нет реального эквайринга, ручной backup не равен автоматическому. Нет обязательного красивого frontend, презентации или повторного экзамена. Ассистент помогает оформить текст на основании фактов, пользователь проверяет воспроизводимость.

Материалы: [GitHub about READMEs](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes) — What your README should contain; собственный docs/domain.md — границы продукта и правила оплаты. Новая библиотека не нужна.
