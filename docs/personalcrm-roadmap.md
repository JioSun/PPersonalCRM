## Цель и границы

Закончить CRM фрилансера: клиент → сделка → счёт → отметка полной оплаты → корректная сводка. Это учёт выставленных и оплаченных счетов, не банковский баланс, не бухгалтерия и не юридически значимый документооборот.

Согласованная первая версия: только USD, без частичной оплаты одного счёта, возвратов и настоящего платёжного шлюза. Клиент подтверждает демооплату по ссылке, обработка идёт через Celery. Остатки вычисляются по счетам. Точные правила отзыва, сроков и конкурентных операций описаны в domain.md.

PDF/email и AI остаются в первой версии по решению пользователя. Их нужно довести до проверенного состояния; перенос больше не является текущим планом. Клиентская страница демооплаты также входит в релиз.

## Правила работы с ментором

1. В работе одна небольшая задача. До кода: ожидаемое поведение и причина дефекта своими словами.
2. Ты предлагаешь решение; я проверяю рассуждение и даю минимальную необходимую подсказку. Готовый код — только по отдельной просьбе.
3. Для содержательного дефекта: воспроизведение/падающий тест → исправление → проходящий тест → объяснение последствий. Тесты не добавляем ради проверки форматирования.
4. Задача закрыта, когда поведение проверено и ты можешь объяснить решение без чтения ответа ИИ.
5. Через 2–3 следующие задачи кратко возвращаемся к предыдущим концепциям. Через неделю — маленькая новая вариация без готового решения.
6. Новую технологию добавляем только под конкретную необходимость. Переписывать весь проект или строить универсальный repository/UoW заранее не нужно.
7. К каждой текущей задаче ментор добавляет 1–3 материала с конкретными разделами, целью чтения и маленьким упражнением. Если концепция неизвестна или забыта, сначала объяснение и пример, затем самостоятельное применение. Вопросы не являются экзаменом без подготовки.

Не ставим срок «до middle». После первых трёх задач фиксируем фактическое время и уточняем оценку остатка. Занятия заканчиваются проверяемым результатом, а не прочитанной главой.

## Что не блокирует первый релиз

Frontend, четыре проекта портфолио, RAG, смена очереди, вынос boilerplate, Kubernetes, микросервисы, универсальный repository/UoW, новый observability-стек, обязательный процент покрытия, искусственный performance benchmark. Измерение запроса добавить, если есть конкретная проблема или учебная цель после исправления корректности.

Transactional outbox не требуется автоматически, но проблема публикации задания и записи в БД существует даже при малой нагрузке. Выбор упрощения нужно явно описать. Идемпотентность рассматриваем там, где повтор создаёт счёт или письмо, а не добавляем механически ко всем PATCH.

## Проверка знания и переход к собеседованиям

Для каждой темы фиксировать уровень: 0 — не объясняю; 1 — объясняю с подсказкой; 2 — объясняю на своём коде и исправляю похожую ошибку; 3 — самостоятельно решаю новый вариант и называю компромиссы. Цель окончания проекта — минимум 2 по всем используемым концепциям, а не звание по числу библиотек.

Темы: Python и исключения; async и блокировки; HTTP и валидация; auth/ownership; ORM и SQL; транзакции и конкурентность; деньги/даты/статусы; миграции; pytest/фикстуры; Redis/кэш; Celery и внешние API для оставленных функций; Docker/CI/эксплуатация.

Финальная защита: объяснить путь запроса, диагностировать незнакомый дефект, добавить маленькое правило с тестом, написать SQL сводки и объяснить конфликт двух обновлений. После этого — персональный план собеседований: Python → SQL → HTTP/backend → практические задачи → обсуждение проекта. Начать пробные интервью можно раньше окончания, если это помогает найти пробелы.

### Материалы к первому заданию

Читать по текущему затруднению, не всю документацию подряд:

1. [FastAPI: Testing Dependencies with Overrides](https://fastapi.tiangolo.com/advanced/testing-dependencies/) — раздел `Use the app.dependency_overrides attribute`. Цель: понять, что словарь использует FastAPI при разрешении Depends; обычный вызов функции не перехватывается.
2. [Python 3.12: Modules, раздел 6.1](https://docs.python.org/3.12/tutorial/modules.html#more-on-modules). Цель: отличать выполнение кода модуля при первом импорте от вызова тела объявленной функции; повторный import обычно использует уже загруженный модуль.
3. [Pydantic Settings](https://docs.pydantic.dev/latest/concepts/pydantic_settings/) — начальный пример Settings, `Environment variable names` и `Field value priority`. Цель: понять загрузку окружения при создании экземпляра, приоритет окружения над dotenv и отсутствие автоматического обновления ранее созданного объекта.

Упражнение без сервисов: написать маленькую функцию, возвращающую строку, и endpoint с Depends на неё. Зарегистрировать override с другой строкой. Предсказать результат HTTP-вызова и прямого вызова функции; затем проверить. Ни БД, ни Redis, ни импорт приложения проекта для этого не нужны.

Наблюдение при повторном чтении кода: пользователь уже перенёс присваивание POSTGRES_DB выше импортов приложения в conftest.py. Это устраняет прежний порядок инициализации при условии, что settings не импортирован ранее другим путём. T01 пока не закрыт: защитная проверка целевого ресурса и безопасный прогон ещё не подтверждены; изоляция Redis также остаётся открытой.
