# PersonalCRM

PersonalCRM — веб-приложение для фрилансеров и самостоятельных специалистов, которые ведут клиентов, сделки и счета. Оно помогает хранить информацию о клиентах, отслеживать состояние заказов и вести учёт сумм и статусов счетов.

## Онлайн-демо

API развёрнут на Render и доступен по HTTPS:

- [Swagger UI — открыть API](https://ppersonalcrm-1.onrender.com/docs).
- [Проверка готовности](https://ppersonalcrm-1.onrender.com/ready).

Основной интерфейс для знакомства с проектом — Swagger UI; отдельная HTML-страница предусмотрена для оплаты счёта. Используйте только вымышленные данные и отдельный пароль для демо.

27 октября 2026 года автор подтвердил ответ `{"status":"ok"}` от `/ready`: API смог обратиться к PostgreSQL и Redis. Это не подтверждает наличие всех таблиц и прохождение полного пользовательского сценария. Сценарий знакомства приведён ниже в разделе «Пройти первый сценарий».

## Демонстрационный режим оплаты

Сейчас приложение не принимает и не переводит реальные деньги. Действие по платёжной ссылке фиксирует оплату внутри системы и обновляет статус счёта. Суммы и статусы используются для учёта работы с клиентами. Интеграция с платёжным провайдером запланирована.

## Возможности

- **Клиенты.** Хранение имени, организации, контактных данных, дополнительных ссылок, заметок, статуса и часового пояса клиента.
- **Сделки.** Создание, просмотр и обновление сделок, отслеживание их статусов. Создание и обновление сделок по текстовым заметкам с помощью ИИ.
- **Счета.** Создание и просмотр счетов, редактирование, подготовка к оплате, отмена, отзыв для редактирования и удаление. Доступность операций зависит от текущего состояния счёта.
- **Платёжные ссылки.** Получение ссылки на счёт для самостоятельной передачи клиенту или отправки по электронной почте. Оплата по ссылке выполняется в демонстрационном режиме.
- **Сводка.** Просмотр сумм оплаченных, неоплаченных и просроченных счетов, списка и количества просроченных счетов, количества клиентов, распределения сделок по статусам и сумм сделок по каждому клиенту.

Для работы ИИ требуется настройка Gemini, для отправки писем — SMTP.

## Технологии

- **FastAPI** — HTTP API, маршрутизация и валидация входных данных.
- **PostgreSQL** — хранение пользователей, клиентов, сделок и счетов.
- **SQLAlchemy** — работа с БД через Python-модели, SQL-запросы и транзакции.
- **Alembic** — управление миграциями схемы БД.
- **Redis** — кеширование сводки и хранение счётчиков для ограничения запросов по IP.
- **Docker и Docker Compose** — контейнеризация приложения и совместный запуск API, PostgreSQL, Redis и миграций.

## Локальный запуск

### Требования

- Git.
- Docker Desktop с включёнными Linux-контейнерами на Windows/macOS либо Docker Engine на Linux.
- Docker Compose v2 (`docker compose`).

Для запуска через Docker отдельно устанавливать Python, uv, PostgreSQL и Redis не нужно. Порты `8000`, `5432` и `6379` на компьютере должны быть свободны.

### 1. Скачать проект

```shell
git clone https://github.com/JioSun/PPersonalCRM.git
cd PPersonalCRM
```

Если репозиторий уже скачан, перейдите в его корневую папку. Все дальнейшие команды выполняются из неё.

### 2. Подготовить настройки

Создайте `.env` из [.env.example](.env.example), только если собственного `.env` ещё нет.

PowerShell:

```powershell
Copy-Item .env.example .env
```

Linux/macOS:

```bash
cp .env.example .env
```

Откройте `.env` в редакторе и заполните настройки:

| Переменная | Назначение |
|---|---|
| `POSTGRES_PASSWORD` | Пароль локальной БД; замените пример своим значением |
| `SECRET_KEY` | Длинный случайный секрет подписи JWT; не используйте пароль БД или значение из примера |
| `SUPER_ADMIN` | Email администратора |
| `MAIN_URL` | Адрес API для формирования платёжных ссылок; локально `http://localhost:8000` |
| `EMAIL`, `PASSWORD`, `EMAIL_HOST`, `EMAIL_PORT` | Настройки отправителя и SMTP-сервера |
| `GEMINI_API_KEY` | Ключ Gemini для работы с текстовыми заметками |
| `GENERAL_TIMEOUT` | Общий бюджет ожидания ответа ИИ в секундах |

Остальные поля сохраните по примеру. В текущем Compose используются `POSTGRES_USER=postgres`, `POSTGRES_DB=personalcrm`, внутренние порты PostgreSQL `5432` и Redis `6379`. Compose переопределяет хосты на `postgres` и `redis` внутри контейнеров.

SMTP и Gemini обязательны для загрузки настроек, но для знакомства с основными CRUD-операциями можно оставить их заглушки из примера. Реальная отправка писем и генерация сделок с такими значениями работать не будут.

Не добавляйте `.env` в Git. Изменение `POSTGRES_PASSWORD` в файле не меняет пароль пользователя в уже созданной БД: первоначальные настройки применяются при инициализации пустого хранилища.

### 3. Собрать и запустить

```shell
docker compose up -d --build
docker compose ps -a
docker compose logs migration
```

Compose запускает PostgreSQL и Redis, ждёт их готовности, затем выполняет `alembic upgrade head` через сервис `migration`. API запускается после успешной миграции. Статус `Exited (0)` у `migration` — нормальный результат: это одноразовая задача.

Откройте:

- [Swagger UI](http://localhost:8000/docs) — интерактивная документация API.
- [OpenAPI JSON](http://localhost:8000/openapi.json) — схема API.
- [/health](http://localhost:8000/health) — проверка работы HTTP-процесса.
- [/ready](http://localhost:8000/ready) — проверка доступности PostgreSQL и Redis; при недоступности возвращает `503`.

API доступен только с этого компьютера: все опубликованные порты привязаны к `127.0.0.1`. Локальная платёжная ссылка также не откроется у клиента на другом компьютере.

### 4. Пройти первый сценарий

Основное управление выполняется через API; для знакомства используйте Swagger UI. Для клиента предусмотрена HTML-страница по платёжной ссылке.

1. Зарегистрируйтесь через `POST /auth/register`, заполнив тело запроса по схеме Swagger.
2. Нажмите **Authorize**. В поле `username` введите email, в поле `password` — пароль. Для прямого вызова `POST /auth/login` данные передаются как форма, а не JSON.
3. Создайте клиента через `POST /clients`, сохраните его `id`.
4. Создайте сделку через `POST /deals`, указав клиента и остальные обязательные поля из схемы.
5. Создайте черновик счёта через `POST /invoices`, связав его со сделкой.
6. Выставьте счёт через `POST /invoices/{invoice_id}/issue`.
7. Получите ссылку через `GET /invoices/{invoice_id}/payment-link` и откройте возвращённый `payment_url` в браузере.
8. Подтвердите демооплату на странице и проверьте состояние счёта и `GET /dashboard`.

Используйте вымышленные данные. Открытие ссылки само по себе не оплачивает счёт. Отправка email — отдельное действие и требует настроенного SMTP.

## Правила работы со счетами

- Счёт принадлежит сделке; сделка — клиенту. Пользователь работает со своими объектами.
- Жизненный цикл счёта: `DRAFT` → `ISSUED` → `PAID`; также предусмотрена окончательная отмена `CANCELLED`.
- Редактирование и физическое удаление доступны для черновика. Выставленный счёт можно отозвать для исправления; прежняя ссылка становится недействительной.
- При выставлении сумма проверяется с учётом уже выставленных и оплаченных счетов сделки.
- Просрочка вычисляется по сроку оплаты в UTC, а не хранится как отдельный статус. Просроченный счёт нельзя оплатить в деморежиме.
- Повторное подтверждение той же успешной демооплаты не должно создавать повторный финансовый эффект.
- В текущей версии используется USD. Реальные переводы, возвраты, частичная оплата одного счёта и конвертация валют не поддерживаются. Для оплаты сделки частями можно создать несколько счетов.

Подробные правила и примеры расчёта остатков: [доменная модель](docs/domain.md).

## Остановка, данные и диагностика

Остановить контейнеры:

```shell
docker compose stop
```

Запустить снова:

```shell
docker compose up -d
```

Удалить контейнеры и сеть, сохранив именованное хранилище БД:

```shell
docker compose down
```

Данные PostgreSQL находятся в volume `postgres_persistence_check` с префиксом имени Compose-проекта. Не переименовывайте его без переноса данных и не используйте `docker compose down -v` для обычной остановки: `-v` удаляет хранилище.

Для диагностики:

```shell
docker compose ps -a
docker compose logs --tail=100 backend migration
docker compose logs --tail=100 postgres redis
```

При ошибке миграции сначала разберите её вывод. Если `/health` отвечает `200`, а `/ready` — `503`, проверьте зависимости и настройки подключения. Смена `.env` требует пересоздания контейнера API:

```shell
docker compose up -d --no-deps --force-recreate backend
```

После изменения Python-кода нужен новый образ. При обновлении схемы сначала создайте резервную копию и явно выполните миграцию перед запуском новой версии API. Подробности: [локальный запуск](docs/local-run.md), [backup и восстановление](docs/backup-restore.md).

Ответы API содержат `X-Request-ID` для сопоставления с журналом ошибок. Не публикуйте `.env`, JWT и секретные токены платёжных ссылок.

## Проверки для разработки

Для этих команд дополнительно нужны **uv и Python 3.12** на компьютере. Они выполняются из корня проекта. `.env` должен быть подготовлен, как в инструкции выше.

```shell
uv sync --locked --python 3.12
uv run --no-sync ruff check backend
uv run --no-sync mypy backend/app
```

Интеграционные тесты используют отдельный [compose.test.yaml](compose.test.yaml): PostgreSQL на `127.0.0.1:55432`, БД `personalcrm_test`, Redis на `127.0.0.1:56379`, логическая БД `5`. Эти ресурсы предназначены только для тестов; их содержимое может очищаться тестовыми фикстурами.

Поднять тестовые зависимости:

```shell
docker compose -f compose.test.yaml up -d --wait
```

Запустить тесты в PowerShell:

```powershell
$env:CRM_TEST_SERVICES = '1'
uv run --no-sync pytest backend/tests
Remove-Item Env:CRM_TEST_SERVICES
```

Или в Bash:

```bash
CRM_TEST_SERVICES=1 uv run --no-sync pytest backend/tests
```

Без `CRM_TEST_SERVICES=1` тесты, требующие соответствующую фикстуру, пропускаются. Не подменяйте тестовые подключения рабочей БД. Схема тестовой БД подготавливается фикстурами Alembic.

После завершения:

```shell
docker compose -f compose.test.yaml down
```

Тестовая БД хранится в `tmpfs` и не предназначена для сохранения данных. Остановка этого окружения не заменяет остановку основного Compose-проекта.

[GitHub Actions](.github/workflows/ci.yml) запускает Ruff, mypy, тесты с отдельными PostgreSQL/Redis и сборку Docker-образа при push и pull request. Результат конкретного запуска следует смотреть в Actions; наличие workflow само по себе не означает, что текущие изменения прошли проверки.

## Развёртывание и документация

Онлайн-демо размещено на Render: API запускается из Dockerfile, PostgreSQL и Key Value работают отдельными сервисами. Render не запускает сервисы из локального `compose.yaml` вместе с API. HTTPS предоставляется платформой.

Настройки подключения задаются в окружении сервиса API. `POSTGRES_SERVER` должен содержать hostname сервиса PostgreSQL, `REDIS_HOST` — hostname Key Value; локальные имена Compose `postgres` и `redis` здесь не подходят. Имя БД, пользователь и пароль должны соответствовать созданной базе. Для публичных платёжных ссылок `MAIN_URL` задаётся как `https://ppersonalcrm-1.onrender.com`.

Миграции `alembic upgrade head` должны быть выполнены отдельно для целевой БД до прохождения сценария. Успешный `/ready` проверяет соединения, но не применяет миграции. Перед изменением схемы нужна резервная копия; возврат старой версии приложения не откатывает схему БД.

`compose.release.yaml` и `Caddyfile` относятся к альтернативному маршруту публикации на VPS и не используются этим деплоем. Воспроизводимый локальный запуск описан выше через `compose.yaml`.

- [Локальный запуск и сохранность данных](docs/local-run.md).
- [Сборка контейнерного образа](docs/container-image.md).
- [Резервная копия и проверка восстановления](docs/backup-restore.md).
- [Учебный гайд публикации на VPS](docs/deployment-guide.md) — описывает маршрут с Caddy, не является подтверждением выполненного деплоя.
- [Доменная модель и правила оплаты](docs/domain.md).

Планируемое развитие — интеграция платёжного провайдера. Текущий деморежим не следует использовать как подтверждение реального поступления денег.
